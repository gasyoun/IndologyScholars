# Как собирать отметки докладов у администратора

Updated: 2026-06-10

Текущая страница `voting.html` работает в статическом режиме GitHub Pages. Она
сохраняет отметки в `localStorage` браузера пользователя и не отправляет их
администратору сайта. Это удобно для личных пометок и ручного экспорта, но не
является полноценной системой голосования.

## Реализованный путь для занятия (Яндекс Форма + кнопка)

Самый быстрый способ узнать, «кто как проголосовал», без своего сервера:

1. **Создайте Яндекс Форму** с полями: `Email заполняющего` (обязательный,
   тип email), `Имя или подпись` (необязательный), `JSON выгрузки`
   (обязательное длинное текстовое поле). Опубликуйте, скопируйте ссылку.
2. **Впишите ссылку в генератор:** константа `VOTE_TEACHER_FORM_URL` в
   `generate_publication_pages.py` (пустая = только копирование). После
   пересборки на странице работает кнопка **«Отправить преподавателю»**:
   она требует email, копирует JSON отметок в буфер и открывает вашу форму —
   студент вставляет JSON в поле и отправляет.
3. **Соберите ответы:** выгрузите ответы формы в CSV.
4. **Сведите «кто как проголосовал»:**
   ```
   python tools/merge_votes.py responses.csv --json-column "JSON выгрузки"
   ```
   На выходе (`analytics_output/votes/`): `votes_by_talk.csv` (по каждому
   докладу — сколько слушали/понравилось и поимённо кто) и
   `votes_by_respondent.csv` (по каждому студенту — сколько отметок).
   Дубли одного email по одному докладу схлопываются по последней выгрузке.

Без Яндекс Формы кнопка «Отправить преподавателю» всё равно копирует JSON —
студент может прислать его письмом, а `merge_votes.py` принимает и папку
с .json/.csv выгрузками: `python tools/merge_votes.py exports/`.

## Что уже есть

- Локальные отметки `Слушал(а)` и `Понравилось`.
- Локальный комментарий к каждому докладу.
- Обязательный email заполняющего перед экспортом или копированием JSON.
- Необязательное имя или подпись заполняющего.
- Экспорт CSV и JSON.
- Копирование JSON для вставки в письмо или сообщение администратору.
- Отсутствие серверного сбора персональных данных.

## Что нужно для автоматической отправки

1. Добавить backend-приемник данных.
2. Отправлять с `voting.html` не только экспортируемый файл, но и POST-запрос.
3. Хранить ответы в таблице или базе данных.
4. Сделать закрытую страницу администратора.
5. Разделить режимы: ответы с идентификацией участника и, если понадобится,
   отдельный анонимный режим.

Без backend администратор не может видеть чужие отметки: статическая страница
на GitHub Pages не принимает и не хранит пользовательские отправки.

## Минимальная схема данных

Для каждой строки ответа стоит хранить:

- `submission_id` - идентификатор отправки;
- `created_at` - время отправки;
- `talk_id` - идентификатор доклада;
- `year` - год программы;
- `heard` - слушал ли пользователь доклад;
- `liked` - понравился ли доклад;
- `comment` - комментарий слушателя;
- `visibility_mode` - `anonymous` или `identified`;
- `respondent_email` - обязательный email заполняющего;
- `respondent_name` - имя или подпись, если пользователь ее указал;
- `user_id` - только для авторизованного режима;
- `source` - версия сайта или страница отправки.

## Вариант 1. Ручной сбор через экспорт

Самый простой и безопасный вариант:

1. Пользователь отмечает доклады.
2. Нажимает `Экспорт CSV` или `Экспорт JSON`.
3. При необходимости нажимает `Скопировать JSON`, если удобнее отправить данные
   текстом без файла.
4. Отправляет файл или JSON редактору по почте, в мессенджере или через форму.
5. Редактор объединяет выгрузки вручную.

Плюс: не нужна авторизация и серверная часть.

Минус: администратор не видит ответы автоматически.

## Вариант 2. Yandex Forms как приемник без своего backend

Да, Yandex Forms можно использовать как быстрый приемник ответов. Это не
полноценная авторизация, но для редакторской сверки достаточно сделать email
обязательным полем и принимать выгрузку из `voting.html` как JSON или файл.
Для публичной формы email остается заявленным идентификатором пользователя.
Если нужна проверка через аккаунт, это лучше делать через Yandex Forms for
Business с ограничением заполнения для сотрудников или выбранных пользователей.

Рекомендуемая структура формы:

1. `Email заполняющего` - обязательный вопрос типа email.
2. `Имя или подпись` - необязательный короткий текст.
3. `Год` - короткий текст или список, по умолчанию `2026`.
4. `JSON выгрузки` - обязательное длинное текстовое поле, куда пользователь
   вставляет результат кнопки `Скопировать JSON`.
5. `Файл выгрузки` - необязательная загрузка CSV/JSON, если удобнее приложить
   файл.
6. `Согласие на идентифицированную редакторскую обработку` - обязательный
   checkbox.

Почему email лучше сделать явным вопросом:

- администратор видит, кто отправил конкретную выгрузку;
- можно отличить независимые свидетельства от повторных отправок одного
  человека;
- можно уточнить спорный комментарий;
- не нужно полагаться на технические следы браузера.

Текущий `voting.html` уже поддерживает этот сценарий: перед экспортом или
копированием требуется email, а в CSV/JSON добавляются `respondent_email`,
`respondent_name`, `visibility_mode`, `exported_at` и `source_page`.

Для полной неанонимности в самой форме нужно:

1. Сделать email обязательным.
2. Не включать отдельную анонимную форму для того же исследования.
3. В тексте формы прямо указать, что ответы видны администратору вместе с
   email.
4. Хранить выгрузки в таблице ответов Yandex Forms и скачивать их для анализа.
5. Если используется Forms for Business, включать дополнительные поля с
   информацией о пользователе при скачивании ответов; для обычной публичной
   формы считать основным идентификатором именно заполненный email.

Ограничение: передавать полный JSON через предзаполненную ссылку технически
неудобно, потому что URL может получиться слишком длинным. Лучше копировать
JSON в длинное текстовое поле или загружать файл.

Официальная документация Yandex Forms:

- создание формы и добавление блоков: <https://yandex.ru/support/forms/en/>;
- тип вопроса `Email`: <https://yandex.ru/support/forms/en/blocks-ref/email>;
- просмотр и скачивание ответов: <https://yandex.ru/support/forms/en/answers>;
- настройка доступа к форме: <https://yandex.ru/support/forms/en/access>;
- ограничения на заполнение: <https://yandex.ru/support/forms/en/restrictions>;
- предзаполнение полей через параметры ссылки, для коротких значений:
  <https://yandex.ru/support/forms/en/pre-fill>.

## Вариант 3. Анонимная отправка

Подходит, если важно собрать общую картину, но не фиксировать личности.

1. На странице добавить кнопку `Отправить анонимно`.
2. Frontend отправляет JSON на endpoint.
3. Backend сохраняет строки без имени, VK ID, email и других прямых
   идентификаторов.
4. Админская страница показывает агрегаты: сколько слушали, сколько отметили
   как понравившееся, какие комментарии требуют ручной проверки.

Для этого подойдут Cloudflare Workers + D1/KV, Supabase, Netlify Functions,
Vercel Functions или Google Apps Script.

Важно: анонимность будет честной только если не сохранять имя, аккаунт, email и
не использовать технические следы как исследовательский идентификатор.

## Вариант 4. Отправка с именем через свой backend

Подходит, если редактору нужно видеть, кто именно оставил отметки.

1. Пользователь входит через выбранный способ авторизации.
2. Сайт получает стабильный `user_id`.
3. При отправке сохраняются отметки, комментарии и идентификатор пользователя.
4. Админская страница показывает две оптики:
   - агрегированную статистику по докладам;
   - таблицу ответов по конкретным участникам.

Этот режим требует явного предупреждения: пользователь должен понимать, что
его отметки будут видны администратору.

## VK ID

VK ID можно использовать как способ входа, если ожидаемая аудитория реально
имеет VK-аккаунты и готова ими пользоваться.

Потребуется:

1. Создать приложение в кабинете VK ID.
2. Получить `APP_ID`.
3. Указать разрешенный `redirectUrl` для сайта.
4. Подключить VK ID SDK или реализовать OAuth-поток.
5. На backend проверить результат авторизации.
6. Сохранять в базе стабильный идентификатор пользователя и, отдельно, его
   отображаемое имя, если пользователь на это согласился.

Официальный web SDK VK ID указывает, что для работы нужен `APP_ID`, а
авторизация поддерживается по OAuth 2.1:
<https://vkcom.github.io/vkid-web-sdk/docs/index.html>.

VK ID не заменяет backend. Он только отвечает на вопрос "кто отправляет".
Вопрос "куда сохранить отправку" все равно решается через серверную функцию или
базу данных.

## Рекомендуемый путь

1. Оставить текущий локальный режим как безопасный черновик.
2. Использовать Yandex Forms как первый приемник идентифицированных ответов:
   email обязателен, JSON вставляется в поле формы или прикладывается файлом.
3. После накопления ответов понять, достаточно ли Yandex Forms для редакторской
   работы.
4. Если нужна автоматическая агрегация прямо на сайте, добавить backend на
   Cloudflare Workers, Supabase, Netlify Functions или Google Apps Script.
5. VK ID подключать только как один из способов входа, а не как единственный
   способ участия.

Такой порядок снижает юридический и технический риск: сначала собирается
идентифицированная редакторская выгрузка через готовый сервис, затем, если
появится необходимость, добавляется собственная автоматизация.
